# AI·EDA 설명형 기술 저널리즘 계약

## 1. 목적

AI판과 EDA판은 새 제품이나 논문이 나왔다는 사실만 전달하지 않는다. 독자가 기술을
이해하고 자기 개발·설계 판단에 연결할 수 있도록 다음 네 질문에 답한다.

1. 이 기술은 어떤 문제를 풀기 위해 나왔는가.
2. 내부에서는 어떤 원리와 단계로 작동하는가.
3. 이전 방식과 비교해 무엇이 달라지는가.
4. 이 변화가 개발·설계 흐름에 어떤 기술적 의의를 갖는가.

심층적이라는 말은 전문 용어, 주의사항, 근거 코드를 많이 적는다는 뜻이 아니다. 입력이
어떤 경로를 지나 결과가 되고, 그 구조가 능력·비용·정확성·설계 선택을 왜 바꾸는지
인과관계를 설명한다는 뜻이다. 쉬운 글은 깊이를 줄인 글이 아니라 구체적인 사용 장면에서
시작해 정확한 구조와 조건으로 단계적으로 들어가는 글이다.

## 2. 기사와 검증 기록의 우선순위

사실 확인과 근거 원장은 모든 기술 기사의 바닥이다. 그러나 본문의 주인공은 검증 절차가
아니라 기술이다.

- 제목·요약·도입부·중심 주장은 기술의 변화와 의의를 먼저 보여 준다.
- version, 가격, license, benchmark 조건, PPA 조건, 재현성, 이해상충은 중심 판단을
  지키는 근거로 둔다.
- 그 보조 정보 자체가 기술 변화의 핵심인 경우가 아니라면 기사 전반을 차지하게 하지
  않는다.
- 벤더 주장과 미확인 범위는 해당 주장 가까이에서 한 번 명확히 밝히고 여러 절에서
  반복하지 않는다.
- 시사판의 찬반 구도, 경고의 병렬 나열, 결론을 유보하는 닫는 질문을 기술적 깊이로
  대신하지 않는다.

## 3. 공통 기사 흐름

AI판과 EDA판은 같은 목차를 복제하지 않고 다음 세 의미 층을 기사마다 자연스럽게
구성한다. 세 층은 전달해야 할 내용이지 고정 소제목이나 고정 순서가 아니다.

1. **뉴스 설명**
   - 무엇이 공개·변경됐고 이번 뉴스의 실제 변화가 무엇인지 먼저 설명한다.
   - 회사 소개, 행사 분위기, 검증 면책보다 독자가 알아야 할 사건과 기술 범위를 앞세운다.
2. **쉽고 심층적인 기술 이해**
   - 구체적인 사용·설계 장면에서 시작해 필요한 만큼 구조와 동작의 인과관계로 들어간다.
   - 주제에 유용한 모듈만 선택한다. 작동 원리, 입력에서 출력까지의 흐름, 이전 기술과의
     차이, 실제로 가능해진 작업, 구현 예, API·runtime 변화, benchmark 설계가 여기에
     들어갈 수 있다.
   - 모든 기사에 비교 대상이나 새 사용 사례가 있는 것은 아니다. 근거 없는 비교와 억지
     활용 예를 만들지 않는다.
3. **기술적 의미와 검증 과제**
   - 앞에서 설명한 기술이 개발·설계 흐름과 제품 선택에 갖는 의미를 판단한다.
   - 적용 범위, trade-off, 한계, 공개되지 않은 조건과 아직 검증되지 않은 결과를 같은
     맥락에서 정리한다.
   - `기술적 의미와 검증 과제`는 사용할 수 있는 자연스러운 소제목의 예일 뿐이며, 기사
     주제에 더 잘 맞는 제목으로 바꿀 수 있다.

작성자는 초고 전에 세 층에서 답할 중심 질문을 정하지만, 기사에 `세 줄 요약`,
`엔지니어를 위한 판단`, `확인된 것과 확인되지 않은 것`, `편집 판단` 같은 시사판형
상자를 기계적으로 넣지 않는다. 소제목은 기술의 구성 요소와 독자의 질문을 따라 정한다.
하나의 절이 두 층을 자연스럽게 연결할 수도 있고, 기술 이해 층은 복수의 절로 깊게
전개할 수도 있다.

이해상충과 취재 조건, 근거 원장, 출처는 본문 뒤 검증 부록으로 둔다. 재현성이나
benchmark 조건은 필요한 주장 가까이에서도 한 번 밝힐 수 있지만, 검증 절차를 별도
본문 서사로 반복해 기술 설명을 끊지 않는다. 근거 부록은 본문의 깊이를 지키는 장치이지
본문의 주인공이 아니다.

## 4. AI판 적용

AI 기사는 모델 이름과 benchmark 순위를 나열하는 대신 다음 연결을 설명한다.

- architecture, training, data, post-training이 관찰된 동작과 어떻게 연결되는가.
- context, memory, reasoning, tool call, runtime이 실제 agent 흐름에서 어떻게 작동하는가.
- 새 방법이 이전 모델·API·개발 방식의 어떤 병목을 바꾸는가.
- 능력·속도·비용·안전의 trade-off가 제품 선택에 어떤 의미를 갖는가.

가격, API alias, checkpoint, license는 중요하지만 기술의 작동 원리와 의의를 밀어내지
않는다. 그 항목이 사건의 본질일 때만 중심 서사로 올린다.

## 5. EDA판 적용

EDA 기사는 벤더 기능 목록과 PPA 숫자를 옮기는 대신 설계 흐름 안에서 기술을 설명한다.

- RTL, netlist, layout, model, constraint 중 무엇이 입력되는가.
- 도구가 어떤 분석·탐색·최적화·검증을 수행하는가.
- 어떤 feedback이 나오고 엔지니어 또는 agent의 다음 행동이 어떻게 달라지는가.
- 기존 flow의 수작업, 반복 횟수, 단계 간 단절, signoff 위험 가운데 무엇을 줄이는가.
- 이 변화가 설계 가능 영역, 수렴 방식, 검증 신뢰도 또는 조직의 역할에 어떤 의의를
  갖는가.

PPA, runtime, node, library, corner, constraint, signoff 단계는 기술 의의를 검증하는
경계 조건이다. 수치가 공개되지 않았더라도 작동 원리와 flow 변화에 충분한 E2 근거가
있다면 설명할 가치가 있다. 반대로 조건 없는 PPA 수치만으로 기술적 의의를 만들지 않는다.

## 6. 편집자 요청 특별판의 각도 보존

AI 특별판은 편집자 브리프에서 요청한 중심 각도를 evidence의
`editorial_brief_alignment`에 기록한다.

- `requested_angle`: 기사가 답해야 할 중심 질문과 의의
- `required_focus_terms`: 제목·summary·도입부·중심 주장에 실제로 나타날 핵심 표현
- `secondary_terms`: version·가격·주의사항처럼 보조적으로 다룰 표현

결정적 출고 게이트는 제목, summary, 첫 세 문단, evidence의 `central_claim`마다 최소 한
개의 focus term이 있는지 확인한다. 네 영역 전체에서는 focus term의 출현 수가 secondary
term보다 많아야 한다. 이 검사는 자연어 브리프를 대신하지 않고, 작성자가 브리프의 중심을
구조화해 기록하고 초안이 그 기록에서 벗어나지 못하게 하는 최소 안전장치다.
